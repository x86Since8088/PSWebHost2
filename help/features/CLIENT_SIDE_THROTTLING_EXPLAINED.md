# Client-Side Request Throttling - 429 Status Codes
**Date**: 2026-02-08
**Issue**: Seeing 429 "Too Many Requests" status codes
**Source**: Client-side (browser), NOT server-side

## Summary

The 429 status codes you're seeing are **entirely client-side** and never reach your server. They're generated by the `RequestThrottleManager` in `psweb_spa.js` to prevent hammering endpoints that recently returned errors.

## How It Works

### Request Throttle Manager (`psweb_spa.js` lines 229-285)

1. **When a request fails** (4xx or 5xx):
   ```javascript
   // Server returns 500 error for /cards/some-card
   RequestThrottleManager.recordFailure('/cards/some-card', 500);
   // URL is blocked for 60 seconds
   ```

2. **On subsequent requests**:
   ```javascript
   // Client checks BEFORE making request
   const throttle = RequestThrottleManager.isThrottled('/cards/some-card');
   if (throttle) {
       // Returns fake 429 response immediately
       // NO network request to server
       return new Response(JSON, { status: 429 });
   }
   ```

3. **When request succeeds**:
   ```javascript
   // Server returns 200 OK
   RequestThrottleManager.clearThrottle('/cards/some-card');
   // URL is no longer blocked
   ```

### Key Configuration

- **Throttle Duration**: 60 seconds (line 233)
- **Triggered By**: Any 4xx or 5xx server response
- **Scope**: Per-URL (each endpoint tracked separately)
- **Storage**: In-memory Map (cleared on page refresh)

## Why You're Seeing 429s Now

### Sequence of Events

1. **Before Server Fix**: Cards returned 500 errors (wrong response format)
2. **Client Response**: URLs throttled for 60 seconds
3. **After Server Fix**: Server now works correctly
4. **Problem**: Client still has URLs in throttle map
5. **Result**: 429 responses for next 60 seconds (even though server is fixed)

## Solutions

### Quick Fix: Clear Throttle Map

Open browser console (F12) and run:
```javascript
RequestThrottleManager.throttledRequests.clear();
console.log('✅ All throttles cleared');
```

### Debug Tool: Visual Throttle Manager

Navigate to: **http://localhost:8080/debug-throttle.html**

Features:
- 📊 Live table of throttled URLs
- ⏱️ Countdown timer for each URL
- 🗑️ Clear individual or all throttles
- 📥 Export throttle data as JSON
- ⚙️ Adjust throttle duration

### Check Throttled URLs

```javascript
// List all throttled URLs
for (let [url, info] of RequestThrottleManager.throttledRequests) {
    const age = Math.floor((Date.now() - info.timestamp) / 1000);
    console.log(`${url} - Status: ${info.status}, Age: ${age}s, Expires: ${60-age}s`);
}
```

### Reduce Throttle Duration (Development Only)

```javascript
// Reduce from 60s to 5s for faster testing
RequestThrottleManager.throttleDuration = 5000;
console.log('⚡ Throttle duration set to 5 seconds');
```

## Identifying Client-Side 429s

### Signs It's Client-Side

✅ Response is **instant** (no network delay)
✅ Browser console shows: `[RequestThrottle] Request throttled due to previous XXX error`
✅ Response body includes: `{ "throttled": true, "retryAfter": XX }`
✅ Response has `Retry-After` header
✅ **Server logs show NO incoming request**

### Signs It's Server-Side

❌ Response has network delay
❌ Server logs show the request
❌ Server code explicitly returns 429
❌ Response doesn't include `throttled: true`

## Why This Feature Exists

### Benefits

1. **Prevents Cascade Failures**
   - Stops browser from hammering broken endpoints
   - Reduces server load during issues

2. **Better User Experience**
   - Prevents rapid-fire error modals
   - Shows clear "retry in Xs" message

3. **Saves Bandwidth**
   - Avoids repeated requests to known-failing URLs
   - Client-side decision (no network round-trip)

4. **Development Safety**
   - Protects against infinite retry loops
   - Makes broken endpoints obvious

### Potential Issues

1. **Sticky Failures**: URL stays blocked even after server fix (60s)
2. **Hard to Debug**: 429 looks like server response but isn't
3. **Per-Tab**: Throttle map not shared across browser tabs

## Production Recommendations

### For Development

```javascript
// In browser console during development:
// Reduce throttle duration
window.RequestThrottleManager.throttleDuration = 5000; // 5 seconds

// Or disable throttling entirely (NOT recommended)
window.RequestThrottleManager.isThrottled = () => false;
```

### For Production

Keep default 60-second throttle duration. It's working as designed to protect against:
- Broken deployments
- Network issues
- Server errors

### Monitoring

Add to your error tracking:
```javascript
// Detect client-side throttling
if (response.status === 429 && response.throttled) {
    console.warn('Client-side throttle active', {
        url: request.url,
        retryAfter: response.retryAfter
    });
}
```

## Code Reference

### Location
`public/psweb_spa.js` lines 229-342

### Key Functions

**`RequestThrottleManager.isThrottled(url)`**
- Returns `false` if not throttled
- Returns object with `{ blocked, status, remainingSeconds, message }` if throttled

**`RequestThrottleManager.recordFailure(url, status)`**
- Called automatically when fetch returns 4xx/5xx
- Adds URL to throttle map with 60-second timer

**`RequestThrottleManager.clearThrottle(url)`**
- Called automatically when fetch succeeds (2xx)
- Removes URL from throttle map immediately

**`RequestThrottleManager.throttleDuration`**
- Default: 60000 (60 seconds)
- Configurable via console

## Testing

### Verify Throttling Works

1. Make request to endpoint that returns 500
2. Check console: `[RequestThrottle] Throttling /path for 60s due to 500 error`
3. Immediately retry same endpoint
4. Should see: `[RequestThrottle] Request throttled due to previous 500 error. Retry in XXs.`
5. Response status: 429 (no network request made)

### Verify Clearing Works

```javascript
// Clear specific URL
RequestThrottleManager.clearThrottle('/cards/system-log');

// Clear all
RequestThrottleManager.throttledRequests.clear();

```
